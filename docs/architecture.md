# Architecture

```
crates/iwr-core   analysis → model → views/layout → guide        (no UI deps; compiles to wasm)
crates/iwr-core/src/c   the C front-end (tree-sitter): items, calls, flow, blocks of `.c` / `.h` files
crates/iwr-ui     Dioxus 0.7 web app → wasm (built by `dx`)
crates/iwr        CLI: axum server, rust-embed of the UI bundle, notify watcher, export
crates/iwr-i18n-gen  build-time generator of the interface texts (TOML → typed functions; see docs/i18n.md)
crates/iwr-core/tests/fixtures/demo  small sample crate the tests analyze
crates/iwr-core/tests/fixtures/cdemo small sample C project (tasks + store) the C tests analyze
```

## Pipeline (iwr-core)

1. `loader` — walk the directory, read every file (sources parsed, the rest shown as text), entry points (`main.rs`, `main.c`) first.
2. `parse` — one front-end per language, both filling the same `Collected` (items, modules, kept bodies as `Body::Rust` / `Body::C`); `SourceFile::lang` says which read a file. **Rust:** `syn::parse_file` per file. File path → module path (`src/a/b.rs` → `crate::a::b`, `crates/foo/src/…` → `foo::…` (or the `[package] name` of `crates/foo/Cargo.toml` when there is one), multi-crate roots hang under a virtual `crate` root). Collects `Item`s (fn, method, struct, enum, trait, impl, alias, const, static), docs, attrs, signatures (token stream re-spaced by `text::clean_tokens`), spans (proc-macro2 `span-locations`). Function bodies kept for pass 2. **C** (`c`, tree-sitter-c, no preprocessing): one module per file under `src/` / `include/` / `lib/` (`src/net/sock.c` and `include/net/sock.h` are both `crate::net::sock`, `main.c` is the root); items for function definitions (prototypes skipped, `static` = private), `struct` / `union` (a struct with the `union` attr) / `enum` with a body, `typedef`s (an alias, or the type itself when it names an anonymous `struct { }`), globals (`Static`, `Const`), `#define`s (`Const` with the `macro` attr, function-like ones a bodiless `Function`; include guards skipped); `#include "x.h"` is a use of module `x`, `<stdio.h>` an external crate. Docs: `/** */`, `/*! */`, `///` anywhere, plain `/* */` or `//` above a top-level definition; the file's first comment is the module doc when marked or followed by a blank line. The code inside `#if` blocks is read as it stands (every branch); a syntax error becomes a diagnostic, the rest of the file is still read.
3. `resolve` — links impls to types/traits; field/signature/alias type relations; per body a `CallVisitor` resolves calls by name (same module first, `self.x()` → owner type, generic bounds + field types as hints, trait decl when receiver is `T: Trait`), tags each call `in_loop`/`in_branch`/`propagated`/`unwrapped`/`awaited`/`recursive`, counts stats; then builds the `Cfg` (`cfg`) and the `Block` tree (`blocks`) of the body. C bodies: `c::body` resolves `f(x)` by name (same module first; calls through pointers stay unresolved) and counts loops / branches / `assert`s; `c::cfg` and `c::blocks` drive the same language-neutral `cfg::Builder` / `blocks::Builder` the Rust walkers use (closures build the branches and loop bodies): `switch` is a `Match` whose cases fall through unless they `break` (`switch_node`, `break` leaves the switch, `continue` the loop around it), `goto` is a `Jump` linked to its label's node, `exit()` / `abort()` a `Halt`, `return -1` / `return NULL` / `return EXIT_FAILURE` a `ReturnErr`, `do … while` a `Loop`; `//` and one-line `/* */` comments above a statement are its note; type names in C signatures and fields resolve through `text::type_names` (words minus the C keywords).
4. `views::build(project, mode, opts)` → `Graph { nodes, edges }` with positions. One builder per mode; `ViewOptions` carries root, module scope, expanded/collapsed node ids, toggles.
5. `layout` — `layered` (Sugiyama-style: cycle removal, longest-path ranks, layer wrapping at `max_per_layer`, dummy nodes for long edges, barycenter ordering, best-of-sweeps + transpose crossing reduction, relaxation, dummy straightening, long edges crossing each layer band straight, ports spread along box sides, component packing into rows); `edge_segments` / `edge_path` / `edge_end` / `edge_samples` are the drawn shape of a route, shared by the canvas and `Graph::label_spots` (label placement that avoids boxes and other labels, nudged off the curve when no spot on it is free; `LayoutEdge::label` widens the gap between the two layers a labelled edge joins so the label fits between the boxes) and `tree` (tidy tree). Returns rects + edge polylines.
6. `guide::build` → `Vec<GuideStep>`: the built-in tour. A `//!` doc with headings / tables / lists is a doc page (`guide::doc_page`): its steps carry a `note` that `script::from_guide` puts in the side panel, section by section; `tours` does the same through `Tour { cues, notes }`. Welcome + one step per module (arch), one per type (types), the call tree, then one chapter per function: its CFG in reading order, told in plain sentences with connectors ("First, … Then … Finally,"). Callees are queued and visited afterwards, breadth first, each once (depth ≤ 6), so the camera never bounces between functions. `GuideStep::part` names the chapter and `refs` carries explicit script refs; `script::from_guide` turns the steps into a `Script`.
7. `script` — codecast format (`parse` / `to_text`, incl. `?` questions on cues and ```` ```mermaid ```` diagram blocks per part), ref resolver (`resolve`: item, block, module, file:line:cols → span), `Script::duration` / `Part::duration` (how long it lasts: from a playing recording's cue times, else guessed from the words, `speech_secs`; shown by the player's title and the plan page, `≈` when guessed), `check` (tracks the sticky `@` view so `!` refs are checked against the diagram's node ids while one is shown). `diagram` — a mermaid-flowchart subset (`parse`: shapes, arrows with labels, `&` sets, nested `subgraph`, front-matter title; tolerant, errors collected) and its layout (`graph`: groups laid out recursively with `layout::layered`, members offset inside their group box, cross-group edges routed by `route_around`: cheapest path on an 8 px grid around boxes, groups the edge is not inside and group titles, square to the box sides, few turns, off the cells earlier arrows took; drawn as straight runs with rounded corners) into the same `Graph` the UI draws for the other views; `Mode::Diagram` is the view, node ids are the refs. `sequence` — sequence diagrams: a `sequenceDiagram` mermaid block (`parse`, stored in `Diagram::seq`, shown by `@ diagram`; refs = participants, `m1…` messages, `n1…` notes; `>` ops hide/show) or generated from the calls of a function (`from_calls`: one column per owner type / module, calls in source order to `depth`, each callee opened once, loops/branches from the `Block` tree as frames; `Mode::Sequence`, `@ sequence:<fn>`); `graph` lays both out as a `Graph`: participant boxes, `Lifeline` edges, activation bars (nodes `a<msg>` carrying the called fn), frames (containers), notes, message edges. `glossary` — glossaries as questions: the **built-in Rust glossary** (`crates/iwr-core/glossary.md`, `include_str!`) and project ones (`glossary.md` next to a codecast), `parse` / `merge` / `mentioned` (whole-word match on a cue's text) / `questions_for`. `speech` — how code is spoken: `segments` (text / code with its spoken form, backtick spans + bare code-looking words), `say_code` (small tokenizer: paths, generics, references, closures, operators → words), `spoken` (TTS text), `pronounce:` overrides, `spell:` acronyms read letter by letter. `chart` — ```` ```chart ```` blocks (`parse`: kind, axes, series, rows) and `{+v2 !v2}` cue markers (`split_say` / `join_say`, `CueMark` = markers + their fraction of the text); `Chart::state` folds the markers fired so far (`script::marks_at(part, cue, frac)`), `range` gives the value axis. `bytes` — byte layouts of ```` ```bytes ```` blocks (`parse`: fields with sizes and formats, `sample:`; `place`: offsets and decoded values); `script::find_side` / `side_at` resolve the `|` side panel. `tutorial` — `fill`: the placeholders (`{dir}`, `{file}`, `{fn}`, `{fn_line}`, `{fn_b1}`) of the UI's tutorial codecast replaced by refs of the open project, in directive lines only, so the recorded text fits every project. `tours` — generated tours: a script line `name_tour[:ref]` (`TOURS`: architecture, types, errors, entry, flow, todo, files) becomes cues built from the project; `script::expand_tours` runs at load (UI, `speak`) and inside `check`. `brief` — compact text brief for LLMs. `prompt` — the prompt the Generate page hands to an AI agent (`PromptOptions` → `build`): the author's wishes only, the rules come from `codecast brief . --guide`. `highlight` — syntax colours for the source panes: a small tolerant Rust lexer (`rust`: one run list per line, multi-line comments/strings split at line ends). `config` — the theme catalogue (`THEMES`), the bundled font catalogue (`FONTS`), and `codecast.toml`, the author's look and defaults (theme, `[colors]`, `[fonts]`, voice, lang, `lock`): `Config` (serde; `from_toml` with `fs`), `problems`, the safe-value checks the UI's `theme::config_css` relies on. `i18n` — codecasts in other languages: `texts` (every readable piece of a script + glossary, markdown cut into lines/cells, code protected by backticks) and `apply` (put translations back, drop the added backticks); `LANGS` with their speech tags. `tr` — what core says to people in each interface language (`i18n/<lang>/*.toml` → `t::views::label_code(lang)`): view names, empty-view notes, item details (`views::item_info_in`, `Item::summary_in`), and the sentences of the built-in tour (`guide`, `GuideOptions::lang`) and of generated tours (`tours::generate(.., lang)`). Told in a language other than English, author text inside them (docs, `//` notes, TODOs) is wrapped in `tr::OPEN`/`CLOSE` and the cue is marked `told`: `i18n::texts`/`apply` then translate only those pieces. `script::Source` (a written script, or the built-in tour) `tell`s a codecast in a language: tours generated in it when core speaks it. `voice` — generated voice: Kokoro `VOICES` / `VOICE_LANGS` (with sample sentences) and the JSON the server and the Generate page exchange (`VoiceStatus`, `VoiceRequest`, `VoiceJob`).

Analysis is syntactic; no type checking. See `resolve_method` for the heuristics and their order.

## UI (iwr-ui)

- `main.rs` — `State` (all `Signal`s, provided via context), fetch + 1.5 s version polling (static mode when `/api/version` is unreachable → `project.json`), keyboard via `document::eval` channel, theme persistence.
- `code.rs` — Code view: `ItemBlock` / `BlockView` render `FnInfo.blocks`; `hover_span` drives two-way highlighting with the source pane.
- `source.rs` — source lines shared by the Code view and the details panel: `shaded` (per file, cached: highlighted lines + gutter colours = innermost item's colour and deepest block's colour, the same as the boxes), `line_body`, `RustText` (coloured signatures and types).
- `canvas.rs` — SVG canvas: pan/zoom transform, `Node`, `Edge` (shape from `layout::edge_segments`, manual arrowheads), `EdgeLabel` (drawn after the boxes at `Graph::label_spots`); boxes have an opaque backing, `Tooltip`, legend, guide highlighting (`focus_nodes`).
- `i18n.rs` — the interface language (`docs/i18n.md`): a global signal read by every generated `t::<module>::<key>()`, picked before the first frame (`?ui=`, `localStorage` `iwr-ui-lang`, `navigator.languages`), `LangPicker` (top bar, Settings › Appearance), `<html lang>`. Separate from the codecast language (`State::lang`); `State::told(lang)` is the codecast retold in a language core speaks, which `translate` and the subtitles start from. `tutorial.rs` picks the tutorial (`assets/tutorial/`, `assets/tutorial/ja/`) by the interface language.
- `panels.rs` — top bar (icon buttons with hover labels), sidebar, details + source. `settings.rs` — settings page (side menu with scroll-spy, card sections; `Row`, `Toggle`, `ThemeGrid`, `FontGrid` are reused by `design.rs`) and its `localStorage` persistence (`iwr-settings` JSON, fonts included). `fonts.rs` — the bundled fonts (`assets/fonts/*.woff2` through `asset!`, URLs made page-relative for exports), their `@font-face`, `resolve` for a `[fonts]` value (bundled id, codecast file, installed name). `icons.rs` — PNG icons embedded with `include_bytes!` and served as data URIs (work from `serve` and from a static export under any sub-path); `assets/icons/*.png` are 48 px black silhouettes recoloured by the `--icon-filter` CSS variable of each theme. `player.rs` — codecast player: parts, cue application (`apply_directives`: view/root/scope, `hl` refs, code mark, camera), `advance()` (next cue, or next part when the full tour is on), TTS via `speechSynthesis` through `document::eval`, recording sync via an `<audio>` element's `timeupdate`, script/audio/glossary loading, questions (`questions()` = script `?` + glossary matches not yet asked; `ask()` pauses and applies the answer's directives, `finish_answer()` restores the cue and resumes). `tutorial.rs` — first start and the tutorial. The tutorial is a codecast in `assets/tutorial/` (part files with placeholders, `index.md`, `NN-part.af_heart.ogg` + `.times` recorded by `codecast voice crates/iwr-ui/assets/tutorial --path crates/iwr-core/tests/fixtures/demo`; a test in `iwr`'s `codecast.rs` fails when a sentence changed since): the parts are `include_str!`, the recordings `asset!`s made absolute against the page URL. The "have you used this app before?" dialog (`iwr-welcomed` in `localStorage`, the top bar's *?* reopens it) starts it. `Spot`: the light of a `+ <spot>` line (`script::UI_SPOTS`, `selector` maps each to the DOM), four dim bands around the target measured every 250 ms, a `.spot-on` ring, the player raised above them. `Zoom`: `+ zoom`, re-aimed every 250 ms. In the Code view a CSS `zoom` on each pane's `.zoom-box` (blocks / source) that holds highlighted blocks or lines, the `zoom-code` class on `.main` narrowing the sidebar; source panes no wider than the lit lines allow. Otherwise a CSS transform on `.main` (a scale and a translate, origin top left) aimed at highlighted files (`HIGHLIGHTS`) or at a panel / spot, measured against the transform it has at that instant; `.app` is `overflow: clip` so scrolling into view never shifts the page. A graph's highlight is not `Zoom`'s: `State::camera` frames the glowing nodes (`frame`). All three stop where the target's biggest text reaches `innerHeight / 56` px (15 to 22; the camera: canvas height / 42) and at 1.6× (pane) / 2.2× (transform). Codecast panels: `State::focus` is the cue's `+` panel (`script::focus_at`), drawn as a `focus-<panel>` class on `.main` whose CSS overrides the panel widths; the canvas re-measures itself and re-aims the camera once the resize is over. Folder refs (`script::resolve_dir`) go to `State::hl_dirs`; a cue that highlights files or folders closes the other folders of the tree (`show_in_tree`). `State::own_script` keeps the project's codecast so the codecast button plays it again after the tutorial. `generate.rs` — the Generate page (top-bar *generate*, `codecast serve` only): `VoiceStatus` from `/api/voice`, language / voice (previewed) / delivery / parts, `POST /api/voice`, and `watch()` (a future in `App`) that follows `/api/voice/job` while a recording runs, then refreshes the status and reloads the script (position kept). `prompt.rs` — its first card, *Write the script with an AI*: a form over `iwr_core::prompt::PromptOptions` (kept in `localStorage` `iwr-prompt`), the live prompt and a copy button. `subtitles.rs` — the caption again in a second language (`State::sub_lang`, `sub_script`: the source script with the translations that already exist put in, same cues): `check_subtitles` counts per language the pieces that have one (`/api/subtitles/LANG`, which never runs the model, or an export's `translations/<lang>.json`), when a script loads and after a translation; `SubPicker` (player and Settings) greys out a language with none, `SubHelp` says what to run (`how_to_make`); `State::subtitle` is shown under the caption unless it repeats it. `chart.rs` — `ChartView`: the SVG of a chart's state at `State::cue_frac` (set by TTS boundaries / audio time), keyed marks with CSS entry animations and transitions; full view for `Mode::Chart`, small in the side panel. `side.rs` — the side panel (`|` lines): byte strip + field table, markdown notes, a still mini diagram; glows `hl_ids`. `md.rs` — markdown subset for guide text, notes and answers (lists, numbered and nested, tables, headings); code tokens rendered with their spoken form (tooltip, or parentheses when the setting is on). `theme.rs` — colors per node/edge kind, legends, `THEMES`, CSS (themes = CSS variables on `.theme-*`); `config_css` turns a `codecast.toml` into `@font-face` + overrides on `.app.app`. `design.rs` — the *Codecast design* editor of the Settings page: a draft `Config` previewed through `apply_config` on every change, saved by `POST /api/config` (fonts uploaded by `POST /api/font/NAME`) or downloaded (`Config::to_toml`). `settings.rs` also has `load_config` / `apply_config`: fetched after the saved settings, each value applied when locked or changed since the config this browser last saw (`iwr-config` in `localStorage`).

Graph is recomputed by `use_memo` from `State::build_graph()` whenever mode/root/scope/expansion/toggles change; layout runs in the browser (wasm), so expanding is instant.

## CLI (crates/iwr, binary `codecast`)

`codecast.rs`: finds the codecast next to a project (`codecast/` dir, `codecast.md`, legacy `codecast.txt`) and reads it; a directory is assembled into one script text by `iwr_core::script::assemble` (part order from `index.md`, sibling `NN-part.mp3` recordings become per-part `audio:` lines, their `NN-part.times` the `times:` lines). `python.rs`: the sidecars' venvs, made by uv (on `PATH`, else installed into `<cache>/codecast/bin` by its pinned installer; it fetches Python too), `<cache>` from `dirs::cache_dir` (moved from `<cache>/iwr` once). `voice.rs`: `codecast voice` — speaks each part file's cues (`speech::spoken`) through the Kokoro sidecar `kokoro_voice.py` (embedded, run in a venv under `~/.cache/codecast/kokoro`), writes `NN-part.ogg` (Opus) + `.times` (start time + text hash per cue); With `--lang ja` it translates each part first (`translate`), phonemizes Japanese with misaki in the sidecar, and writes `NN-part.ja.ogg` + `.ja.times` (hashes of the English cues); the loader adds them as `audio.ja:` / `times.ja:` lines (`Part::voices`) and `i18n::use_voices` makes them the parts' recordings once the player has translated the script. `voice::record` reports `Event`s (stage, plan, cue, part written, log) and stops on a cancel flag; the sidecar streams `@ready` / `@cue` / `@part` lines on stderr, and each part's `.times` is written as soon as its file is, so a cancelled run keeps what is done. Recordings are one per language and voice (`codecast::variant_stem` / `parse_variant`: `01-welcome_en_am-adam`, `01-welcome_ja_jf-alpha`; older `01-welcome` / `01-welcome_ja` are renamed by `voice::migrate`, older dotted names `01-welcome.ja.jf_alpha` and their videos by `codecast::migrate_names` when the directory is loaded); the loader makes them `Voiced { lang, voice }` (`audio.en.am_adam:` lines) and the player picks one (`State::recording_voice`, `i18n::use_voices(s, lang, voice)`, the `VoicePicker` chip). `voice::status` (per part, language and voice: recorded / stale / own; `stale` groups with the header's delivery; `orphans` = files of parts that are gone; `/api/voice/refresh` records the groups again, `/api/voice/clean` deletes them); `sets` = every language and voice (or pair) with recordings, its recorded / stale / missing parts and delivery, shown by the Generate page's *Recorded voices* card: `/api/voice/complete` records what a set lacks with the voice and delivery it was made with, `/api/voice/drop` deletes all its files and `voice::preview` serve the UI's Generate page through `/api/voice*` (`serve.rs` keeps one `VoiceJob` at a time); the shared JSON types, voices and languages are in `iwr_core::voice`. `codecast::load` drops a recording whose hashes no longer match (`Loaded::stale`) and the player's `uses_tts()` speaks that part by TTS. `video.rs`: `codecast video` — starts `codecast serve` as a child, a `chromium-headless-shell` with `--enable-begin-frame-control`, and talks DevTools to it over a websocket (`Cdp`, one command at a time); per part it opens `/?render=N&voice=V&lang=L&sub=S` (the player's render mode: `State::start_render`, class `.app.render` hides the chrome, `window.__codecastTime(t)` feeds the time the audio element would, `window.__codecastReady` says the translation, recording and subtitles are in, `__codecastError` why not), then per frame sets the time, advances virtual time by one frame (`Emulation.setVirtualTimePolicy`) and draws it (`HeadlessExperimental.beginFrame`, `frameTimeTicks` on `CLOCK_MONOTONIC` so CSS animations follow the same clock as JS), piping the JPEGs into ffmpeg with the part's recording. `docker/video/Dockerfile` builds it with Chromium, ffmpeg and Noto fonts; without Chromium and ffmpeg on `PATH`, `video::in_docker` builds that image from the repository the binary came from (`CARGO_MANIFEST_DIR`) and runs the same command in it, mounting the project, codecast, output and the host's translation cache (read-only: the image has no model) under `/mnt/N`, with `CODECAST_VIDEO_IN_DOCKER` set so nothing is recorded there. Given `--voice`, `codecast video` first runs `voice::run` for that voice and language (on the host), so missing and stale parts are recorded before filming. `translate.rs`: offline translation for `codecast translate`, `POST /api/translate/LANG` and `export --lang` — Argos models through the sidecar `translate_sidecar.py` (`ctranslate2` + `sentencepiece`, venv and models under `~/.cache/codecast/translate`), cache `<lang>.json` there; an author's own `translations/<lang>.json` next to the codecast (made with another tool from `codecast translate --pieces`) wins piece by piece, and when it covers everything the model is not used. The player (`State::set_lang` / `translate`) keeps the English script in `script_src`, translates it with `i18n`, and speaks it with a voice of that language; recordings only play in English. `/api/codecast/NAME` serves those recordings; `/api/glossary` the project glossary (`glossary.md` next to the script); `/api/config` the `codecast.toml` as JSON (`codecast::read_config`, `check_config`), its fonts through `/api/codecast/PATH` (`is_safe_asset_name`: recordings and fonts, no path escapes); `export` writes it as `codecast.json` and copies the fonts to `codecast/`. `POST /api/config` and `POST /api/font/NAME` write them (the editor in Settings); since CORS is open for reads, writes check `same_origin` (loopback `Host`, `Origin` equal to it).

`serve.rs`: `analyze()` → `Arc<Project>` in `RwLock`; `notify` watcher debounced 250 ms triggers re-analysis and bumps `/api/version`. Assets come from `target/dx/iwr-ui/release/web/public` via `rust-embed` (`build.rs` creates the folder so the crate compiles before the UI is built). `export()` copies assets, rewrites `"/./assets/` → `"./assets/` in html/js so the site works from any sub-path, and writes `project.json`.
