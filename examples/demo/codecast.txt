# A tour of the demo task runner

## Welcome
@ arch
Welcome to the demo task runner. It is a tiny program that reads a list of tasks from text, stores them, and runs them in priority order, with a parser, a scheduler and a storage backend.
It exists to exercise everything IwannatRust can show: calls, branches, loops, recursion, traits and error propagation. So let's use it as a guided walk through the tool itself.
We start with the big picture. This is the architecture view: every box is a module, and the arrows between them show who depends on whom.
! crate::parser
The parser module turns text lines into tasks. It is the first thing the program touches, and the first place things can go wrong.
! crate::storage
The storage module keeps the tasks. It hides the actual container behind a trait, so a database could replace the in-memory map without touching the rest.
! crate::scheduler
The scheduler decides what runs next. Each round it asks the storage for everything and picks the heaviest task.
! crate::model
And the model module holds the shared data: what a task is, how urgent it is, and a small trait for describing things.
!
Four modules, one entry point in main.rs, and the arrows all point inward to the model. That is the whole map; now let's look at the data they share.

## The data
@ types
This is the types view. Structs and enums hold the values, traits describe behaviour several types can share. Green arrows mean contains, purple dashed arrows mean implements.
! crate::model::Task
A task is just a name, a priority and a number of steps. Nothing else.
! crate::model::Priority
Priority is an enum with three levels: low, normal and high. The scheduler turns it into a weight, we will see how.
! crate::storage::Storage crate::storage::MemoryStorage
Storage is the trait, with save, take and list. MemoryStorage is its only implementation, backed by a HashMap keyed by task name.
! crate::model::Describe
Describe is a tiny trait with one required method and one default method built on top of it. Task implements it so the scheduler can log what it picked.
! crate::AppError crate::parser::ParseError crate::storage::StorageError
Then the three error types: the parser and the storage each have their own, and AppError at the top wraps both. Keep them in mind, we come back to them at the end.
!
Now that we know the data, let's follow the program as it runs.

## How a run works
@ flow:crate::run
Everything starts in main, which only prints a banner and calls run. So run is where the story is, and we will stay here for a while. This is its control flow: every box is a statement, and the edges are the paths execution can take.
! crate::run/b1
= src/main.rs:49:17-44
First, run hands the whole input to the parser and gets a list of tasks back.
= src/main.rs:49:41-41
Notice the question mark at the end of that line. It means: if parsing fails, stop right here and give the error to main. We never reach the rest of the function.
! crate::run/b2 crate::run/b3
Then the first decision. If the list came back empty, run refuses to go on and returns the Empty error. This is the early exit you see leaving the graph on the right.
! crate::run/b4
Otherwise it creates an in-memory storage.
! crate::run/b5 crate::run/b6
= src/main.rs:55:32-32
And saves every task into it, one per loop iteration. Saving can fail too, a duplicate name for instance, so the question mark is back, inside the loop this time.
! crate::run/b7 crate::run/b8
With the tasks stored, run builds a scheduler on top of the storage and starts a counter.
! crate::run/b9
= src/main.rs:59:5-44
Now the main loop. It keeps asking the scheduler for the next task until the scheduler answers None, which happens when the storage is empty.
@ code:crate::run
! crate::run/b10 crate::run/b11
= src/main.rs:60:12-53
Let's read that loop as code. Inside it there is a small rule: once three tasks have run, low priority tasks are skipped with a continue.
! crate::run/b12 crate::run/b13
Every other task is executed, and the counter goes up.
! crate::run/b14
When the loop ends, run returns how many tasks it executed, wrapped in Ok. So run has three ways out: two errors and one success. Next, let's see what executing a task means.

## Executing a task
@ flow:crate::execute
execute is the smallest function with the most interesting shape, because it calls itself. This is its control flow.
! crate::execute/b1 crate::execute/b2
It starts by printing the task name, indented by the current depth.
! crate::execute/b3
Then it loops over the task's steps.
! crate::execute/b4
Each step is a decision: even steps become a sub-task, odd steps are skipped.
! crate::execute/b5 crate::execute/b6
= src/main.rs:76:13-36
For an even step it builds a sub-task with zero steps and calls execute again, one level deeper. That is the recursion: the orange dashed edge in the call tree.
! crate::execute/b5
The base case is hidden in the sub-task itself: it has zero steps, so the inner call prints its name, its loop runs zero times, and it returns. The recursion is always exactly one level deep.
! crate::execute/b7 crate::execute/b8
Odd steps just print a skip message. And that is all of execute. Now let's go back to the beginning of the data flow: the parser.

## Parsing a line
@ code:crate::parser::parse_all
The parser is three small functions. parse_all is the entry: it walks the lines, skips empty ones, and collects a task per line.
! crate::parser::parse_all/b2 crate::parser::parse_all/b3 crate::parser::parse_all/b4
Blank lines are skipped with a continue, so a trailing newline is not an error.
! crate::parser::parse_all/b5
Every other line goes through parse_line, and again the question mark means the first bad line stops everything.
@ code:crate::parser::parse_line
! crate::parser::parse_line/b1
parse_line does the real work. It splits the line on colons and takes the pieces one at a time.
! crate::parser::parse_line/b2 crate::parser::parse_line/b3 crate::parser::parse_line/b4
Each piece is optional, because the line may be too short. ok_or turns that None into a MissingField error, and the question mark sends it up. Three fields, three chances to fail.
! crate::parser::parse_line/b5
The priority text goes through parse_priority, a match on the three allowed words that returns BadPriority for anything else.
! crate::parser::parse_line/b6
And the step count is parsed as a number, with a BadNumber error if that fails.
! crate::parser::parse_line/b9
Only when all of that succeeded does a Task get built. Five question marks in nine lines: this is what error propagation looks like in Rust. Next, the other half of the program: how tasks get picked.

## Scheduling
@ flow:crate::scheduler::Scheduler::next_task
next_task is the heart of the scheduler. It returns an Option: a task, or None when there is nothing left.
! crate::scheduler::Scheduler::next_task/b1
It starts by asking the storage for every task it has. This goes through the Storage trait, so the scheduler never knows it is talking to a HashMap.
! crate::scheduler::Scheduler::next_task/b2
Then it finds the task with the highest weight. max_by_key returns None on an empty list, and the question mark turns that into an early None for the whole function.
@ code:crate::model::Task::weight
! crate::model::Task::weight/b2
The weight is where Priority becomes a number: high counts a hundred, normal ten, low one, plus the number of steps. So a high task always beats a normal one, whatever its size.
@ flow:crate::scheduler::Scheduler::next_task
! crate::scheduler::Scheduler::next_task/b6
Back in next_task, the winner is removed from the storage by name. take returns a Result, and ok() turns an error into None, so a missing task also ends the loop quietly.
! crate::scheduler::Scheduler::next_task/b8
Finally it logs what it picked, using the Describe trait we saw earlier, and hands the task back. That closes the main loop in run. Now, the errors.

## Where errors go
@ errors
This is the error flow view. It shows every function that can fail, every error type, and how errors travel between them.
! crate::parser::ParseError crate::storage::StorageError
The parser and the storage each have their own error enum, close to where the problems happen.
! crate::AppError
All of them funnel into AppError, the type run returns to main.
! crate::AppError::from
The two From implementations are what make that work. The question mark calls From automatically, so a ParseError becomes AppError::Parse without a single match in run.
! crate::main
main is the only place that looks at an error: it prints it and exits with code one. Everything below it just passes errors up.
!
That is the whole error story: three enums, two conversions, one handler. To finish, let's see where all of this lives in the files.

## Where things live
@ code:src/main.rs
main.rs holds the entry point, the top level error type with its conversions, the run function and execute.
@ code:src/parser.rs
! crate::parser::parse_line
parser.rs is the three parsing functions we just walked through.
@ code:src/storage.rs
! crate::storage::Storage
storage.rs declares the Storage trait first, then the in-memory implementation below it.
@ code:src/scheduler.rs
! crate::scheduler::Scheduler
scheduler.rs is generic over any Storage, which is why it never mentions MemoryStorage.
@ code:src/model.rs
! crate::model::Describe
model.rs ends with the Describe trait: a default method built on top of one required method.
!
And that is the end of the tour. You have seen every view: architecture, types, control flow, code, errors and the files. Click any box to explore on your own.
